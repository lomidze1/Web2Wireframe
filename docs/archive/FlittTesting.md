<critical_rules>
1. **Sequential execution** — სანამ 1 ტესტი არ დადასტურდება PASS-ად, მეორე ტესტზე **არანაირად** არ გადახვალ. გამოტოვება მხოლოდ მომხმარებლის **მკაფიო** დასტურის შემთხვევაში (`SKIPPED — approved by user on YYYY-MM-DD`).
2. **Only real tests** — code review, "looks correct", ან "tests pass in CI" **არ ითვლება** PASS-ად. PASS = რეალურად შესრულდა (curl, manual click-through, real Flitt sandbox/prod call, screenshot, log line).
3. **Bilingual rows** — Test name + Notes ორივე ენაზე (KA / EN). მცირე ცხრილში ერთი row შეიძლება, მაგრამ Test name სვეტი ყოველთვის ორივე.
4. **Flitt-mandated tests** — თუ ტესტს Flitt-ი თვითონ ითხოვს (preflight, certification checklist, docs.flitt.com-ის რომელიმე გვერდი), `Flitt-Required?` სვეტში ჩაწერე `YES + <URL>`. სხვა შემთხვევაში `no`.
5. **Money cost transparency** — თუ ტესტი მოითხოვს რეალურ გადახდას (real card, real charge), `Cost` სვეტში ჩაწერე ზუსტი თანხა (`$1.00` ან `$16.00 (refundable: no — Flitt no-refund policy)`). სანამ მომხმარებელი არ დაუშვებს, **არ გაუშვა**.
6. **Failure evidence** — FAIL-ის შემთხვევაში `Notes` სვეტში: (a) რა მოლოდინი იყო, (b) რა მოხდა რეალურად, (c) error log/curl response, (d) სავარაუდო მიზეზი, (e) blocker თუ მხოლოდ minor.
7. **No silent edits** — როცა row-ს განაახლებ, `Last updated` სვეტი ყოველთვის შეცვალე. `Verified by` სვეტში ჩაწერე `Claude` (შენ), `User` (მომხმარებელი), ან `Both`.
8. **Never log secrets** — Notes-ში ნუ ჩაწერ რეალურ `SECRET_KEY`, full webhook signature, ან card numbers. იყავი `***-suffix-only` ფორმატით (მაგ: `mid: 1549901, key: ***ab12`).
9. **CLAUDE.md compliance** — `USE_PRODUCTION` toggle წესი დაიცავი (git commit-მდე უნდა იყოს `false`). `.env` ფაილი **ნუ წაიკითხავ** პირდაპირ (user-მა აკრძალა, იხ. memory `feedback_never-read-env.md`) — env var-ების validity-ს ამოწმე endpoint-ის response-ით ან მომხმარებლის manual verification-ით.
</critical_rules>

<workflow>
For each NOT_STARTED row in the test catalog (top-to-bottom):

1. **Announce** — ერთი წინადადებით უთხარი user-ს: "ვიწყებ ტესტ #N — <test name>".
2. **Mark IN_PROGRESS** — Status სვეტი → `IN_PROGRESS`, Last updated → ახლანდელი თარიღი.
3. **Execute** — გააკეთე ერთი ან რამდენიმე ქმედება:
   - Code-level: read source, run unit test, curl local endpoint
   - Sandbox: real call to Flitt sandbox (test merchant ID)
   - Production: only if user explicitly approves AND test requires it
   - Manual: ask user to click through (e.g., complete payment in browser)
4. **Wait if needed** — თუ ტესტი მოითხოვს user action-ს (real card payment, Flitt dashboard check, Figma plugin click), **გაჩერდი** და სთხოვე confirmation. ნუ ჩაწერ PASS სანამ user-ი არ დაგიდასტურებს.
5. **Record evidence** — Evidence სვეტში ჩადე ერთი ან რამდენიმე:
   - `curl: <command> → <response snippet>`
   - `commit: <sha>`
   - `screenshot: <path or "user-confirmed">`
   - `log: <one-line excerpt>`
   - `unit-test: <test-name> pass`
6. **Update status** — `PASS` / `FAIL` / `BLOCKED` / `SKIPPED`.
7. **Update Verified by + Last updated**.
8. **Brief user** — ერთი წინადადებით: "ტესტი #N — PASS. გადავდივარ #N+1-ზე."
9. **STOP if FAIL or BLOCKED** — ნუ გადახვალ შემდეგზე. დაელოდე user-ის გადაწყვეტილებას (fix? skip? defer?).
</workflow>

<output_format>
ცხრილის სვეტები (ნუ შეცვლი ბრძანების გარეშე):
| # | Test name (KA / EN) | Category | Flitt-Required? | Cost | Status | Verified by | Last updated | Evidence | Notes (KA / EN) |

Status enum: `NOT_STARTED` | `IN_PROGRESS` | `PASS` | `FAIL` | `BLOCKED` | `SKIPPED`

Category enum: `Setup` | `Checkout` | `Signature` | `Webhook` | `Subscription` | `License-State` | `Security` | `Edge-Case` | `Production-Readiness`

Beneath the test catalog, maintain three living sub-sections:
- **Environment Snapshot** — env vars, merchant IDs, base URLs (masked)
- **Open Blockers** — FAIL ან BLOCKED rows-ის სია, რანკ პრიორიტეტით
- **Session Log** — append-only ჟურნალი თარიღი + ერთი წინადადება რა გავაკეთე
</output_format>

<antipatterns>
- ❌ "Looks good in the code, marking PASS" — code review არ არის ტესტი
- ❌ "All unit tests pass, so checkout works" — unit ≠ integration
- ❌ "Probably works since signature lib is well-tested" — verify, don't guess
- ❌ Batch updates ("marked 5 tests as PASS") — every PASS needs its own evidence
- ❌ Skipping rows because "we'll come back" — explicit SKIPPED + user approval or don't skip
- ❌ Hiding failures in Notes — FAIL is FAIL, mark it
</antipatterns>
